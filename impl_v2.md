# Implementation V2: Multi-Protocol Roadmap

## 1. Confirmed product direction

This application is an internal traffic source for testing the Brabo.io platform. It must generate realistic industrial data that Brabo.io consumes through a selected protocol.

Confirmed constraints:

- Primary industries are chemical, pharmaceutical, and automotive, while keeping the design usable across industries.
- A test operator selects a protocol and configures the tags exposed or published by that protocol.
- Every relevant tag attribute must be configurable; the same tags do not need to be exposed by every protocol.
- Dependencies must be open source. Commercial protocol toolkits are out of scope.
- The supported runtime is Ubuntu 22.04 or a similar Linux container environment.
- Formal protocol or product certification is not required because this is an internal traffic-generation tool.
- Interoperability with the Brabo.io collector is the release criterion.
- The first additional protocol interface is the OpenOPC/Pyro compatibility layer documented in `impl_opcda.md`.

The simulator has two traffic delivery modes:

| Mode | Protocol examples | Simulator role | Brabo.io role |
| --- | --- | --- | --- |
| Pull/subscribe | OPC-UA, Modbus TCP | Server or simulated device | Client that reads, polls, writes, or subscribes |
| Push/publish | MQTT, Sparkplug B, OPC-UA PubSub | Publisher/client | Subscriber directly or through a broker |

Built-in virtual clients may remain for self-test and background-load scenarios, but Brabo.io consumption—not traffic generated by clients talking back to the simulator—is the primary product flow.

## 2. Recommended protocol portfolio

Given the confirmed industries and Linux/open-source constraints, protocols should be prioritized as follows:

| Priority | Protocol | Recommendation | Why |
| --- | --- | --- | --- |
| 1 | OpenOPC/Pyro compatibility | Implement first | Matches the Brabo.io traffic-consumption requirement without COM/DCOM |
| 2 | Modbus TCP | Build next | Widely used, cross-platform, and straightforward to simulate as both server and client |
| 3 | MQTT 5 with Sparkplug B | Build after Modbus | Strong IIoT, SCADA, MES, broker, and cloud integration |
| 4 | OPC-UA PubSub | Add when Brabo.io supports UA streaming | Natural extension of the existing OPC-UA data model |
| 5 | EtherNet/IP | Customer-driven automotive pack | Relevant to PLC-heavy automotive environments but more complex |
| 6 | Siemens S7 | Customer-driven automotive pack | Relevant when Brabo.io must emulate Siemens PLC ingestion |
| 7 | BACnet/IP | Optional industry pack | Useful outside the core verticals for building automation |
| 8 | DNP3 or IEC 60870-5-104 | Optional industry pack | Useful outside the core verticals for utilities and telecontrol |
| Deferred | Native OPC-DA COM/DCOM | Research only under current constraints | Classic DA hosting conflicts with Ubuntu-only deployment |
| Deferred | PROFINET | Do not implement without a concrete requirement | Real-time behavior and device conformance make it a poor fit for the initial container simulator |

The recommended default product scope is:

> OPC-UA + OpenOPC/Pyro + Modbus TCP + MQTT/Sparkplug B on Ubuntu containers, followed by customer-driven automotive protocol packs.

This combination covers the strongest cross-industry ingestion paths for chemical, pharmaceutical, and automotive testing while remaining practical with open-source Linux components.

## 3. Scenario and adapter architecture

Do not add each protocol directly to the current producer loop. First introduce scenario, tag, signal, and adapter abstractions.

```text
                               Dashboard and REST API
                                         |
                               Simulator lifecycle
                                         |
                         Scenario TagCatalog/ValueStore
                           |          |          |
                           |          |          +--> MQTT/Sparkplug publisher
                           |          +-------------> Modbus TCP adapter
                           +------------------------> OPC-UA adapter
```

Each configured scenario owns a protocol, a tag catalog, a traffic profile, and fault settings. Different scenarios may define completely different tags. An optional future `signal_group` can deliberately link a value across protocols, but cross-protocol identity is not required.

Every adapter should consume a protocol-neutral tag definition and value sample:

```text
TagDefinition
  key
  browse_name
  browse_path
  canonical_type
  writable
  engineering_unit
  description
  scale
  metadata
  protocol_mapping

TagSample
  key
  value
  quality
  source_timestamp
  sequence
```

Values should be generated once per tag per producer tick. The selected adapter translates that sample into its protocol-specific representation.

Suggested top-level model:

```text
SimulationScenario
  id, name, enabled
  protocol
  protocol_config
  tags[]
  traffic_profile
  fault_profile
  duration
```

`protocol_mapping` is a tagged structure whose fields depend on the selected protocol—for example, OPC-UA NodeId/browse path, Modbus area/address/word order, or MQTT topic/Sparkplug metric identity.

Each adapter should implement a common lifecycle contract:

```python
class ProtocolAdapter:
    async def start(self, catalog, values) -> None: ...
    async def stop(self) -> None: ...
    def status(self) -> dict: ...
    def metrics(self) -> dict: ...
```

Failures in one scenario or adapter must not stop other scenarios. Each adapter needs bounded queues, protocol-specific health, and separate counters.

## 4. Modbus TCP: highest priority

Modbus TCP should be the next protocol implemented.

Add:

- A Modbus TCP server exposing simulated coils and registers.
- Server-side request/connection instrumentation showing traffic consumed by Brabo.io.
- Optional virtual Modbus clients only for self-test, background load, and fault verification.

The Modbus Organization publishes the protocol and TCP implementation guidance through its [official specifications](https://www.modbus.org/modbus-specifications).

### Data mapping

| Simulator value | Modbus representation |
| --- | --- |
| Boolean | Coil or discrete input |
| 16-bit integer | Holding or input register |
| 32-bit integer | Two registers |
| Float | Two registers with configurable word order |
| Double | Four registers |
| Writable tag | Coil or holding register |
| Read-only tag | Discrete input or input register |

Modbus does not provide native timestamps, quality, browse hierarchy, or subscriptions. Clients poll numeric addresses, so the simulator must publish an explicit, stable register map.

### Required configuration

- Enabled state and listen address
- TCP port
- Unit ID or multiple simulated unit IDs
- Starting address for each register area
- Signed and unsigned encoding
- Float/double byte and word order
- Maximum registers per request
- Client request rate and function-code mix
- Request delay, timeout, disconnect, and exception injection
- Duplicate address and register-overlap validation

Use a configurable unprivileged application port such as `1502` by default in development. A container or host port mapping can expose standard TCP 502 where required.

### Initial server operations

- Read Coils (`01`)
- Read Discrete Inputs (`02`)
- Read Holding Registers (`03`)
- Read Input Registers (`04`)
- Write Single Coil (`05`)
- Write Single Register (`06`)
- Write Multiple Coils (`15`)
- Write Multiple Registers (`16`)

Add less common function codes only when a target product requires them.

### Modbus acceptance criteria

- Stable register map is available through the API and dashboard.
- Boolean, integer, Float, and Double round-trip tests pass for every configured byte/word order.
- Multiple unit IDs can expose different device models.
- External clients and built-in virtual clients can operate simultaneously.
- Invalid functions, addresses, and values produce correct Modbus exceptions.
- Polling, writes, disconnects, delays, and exception injection have separate metrics.

Estimated effort: low to medium compared with the other proposed protocols.

## 5. MQTT 5 and Sparkplug B: strategic priority

The application should act as an MQTT client connecting to an external broker. It should not embed a production broker.

Support two publishing modes:

1. Simple MQTT JSON topics for easy development and integration testing.
2. Sparkplug B for interoperable industrial and SCADA simulation.

MQTT provides lightweight publish/subscribe transport and QoS levels. Sparkplug adds an industrial topic namespace, typed metrics, discovery, and online/offline state management. See the [OASIS MQTT 5 standard](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html) and [Eclipse Sparkplug specification](https://sparkplug.eclipse.org/specification/).

### Simple MQTT mode

Support:

- Configurable topic prefix
- Per-tag or batched JSON messages
- QoS 0, 1, and 2
- Retain configuration
- Publish interval and change-only publishing
- Username/password and client certificates
- TLS hostname and certificate validation
- Command topics for writable values
- Last Will and Testament
- Reconnect and offline buffering with bounded queues

Example topic model:

```text
simulator/{instance}/tags/{tag-key}
simulator/{instance}/commands/{tag-key}
simulator/{instance}/status
```

### Sparkplug B mode

Support at minimum:

- `NBIRTH` and `DBIRTH`
- `NDATA` and `DDATA`
- `NDEATH`
- `NCMD` and `DCMD`
- Sequence numbers
- Birth certificates and rebirth requests
- Typed metrics
- Node and device templates where useful
- Correct broker session and Last Will behavior
- QoS configuration
- TLS and broker authentication
- Simulated connection loss and reconnect
- Multiple edge nodes and devices

Use an existing conformant Sparkplug encoding library where possible and validate with the Sparkplug Technology Compatibility Kit or compatible applications.

### MQTT/Sparkplug acceptance criteria

- The simulator reconnects without unbounded message growth.
- Birth, data, death, command, sequence, and rebirth behavior is correct.
- Commands update the owning scenario's value store and are reflected in subsequent MQTT/Sparkplug data messages according to the configured write policy.
- Broker loss and recovery can be injected and observed.
- TLS and credential failures do not leak secrets into logs.
- Broker, publish, command, reconnect, dropped, and coalesced-message metrics are available.

Estimated effort: medium.

## 6. Native OPC-DA COM/DCOM: deferred research item

Native OPC-DA COM/DCOM hosting is not part of the committed Linux V2 scope. The implemented OpenOPC/Pyro compatibility interface is documented separately in `impl_opcda.md`; keep `opc-da.md` as a feasibility and contingency document for a true COM/DCOM server.

Reconsider it only when Brabo.io needs a verified Classic DA ingestion test and the team accepts an explicit platform exception or the risk of an experimental cross-platform implementation.

- Existing SCADA or HMI software that only supports OPC-DA.
- Windows-based interoperability testing.
- DCOM failure and recovery testing.
- OPC-UA migration validation.

OPC Classic is COM/DCOM-based according to the [OPC Foundation](https://opcfoundation.org/about/opc-technologies/opc-classic/). A conventional implementation needs Windows, while the confirmed product runtime is Ubuntu 22.04 or a similar Linux container. Commercial gateways and SDKs are also excluded.

The only in-policy investigation path is an open-source proof of concept that runs in the supported Linux container. It must be tested directly against the Brabo.io DA consumer. An alpha or incomplete DCOM stack must not be represented as supported merely because a demonstration connects.

Estimated effort and risk: very high. Default decision: defer.

## 7. OPC-UA PubSub

OPC-UA PubSub is a logical extension when users need one-to-many streaming rather than OPC-UA client/server sessions.

Possible modes:

- UADP over UDP multicast for local industrial networks.
- OPC-UA JSON or UADP over MQTT for broker-based distribution.

OPC-UA PubSub supports brokerless and broker-based models, including UDP and MQTT mappings. See [OPC UA Part 14](https://reference.opcfoundation.org/specs/OPC-10000-14/1).

Add it after MQTT/Sparkplug unless a specific UA PubSub consumer is already waiting. First evaluate suitable libraries because the current application does not implement PubSub through its `asyncua` usage.

Required work includes:

- PublishedDataSet configuration
- Publisher, writer group, and DataSetWriter identities
- DataSet metadata and configuration-version changes
- Key-frame and delta-frame behavior
- UADP or JSON encoding
- UDP multicast or MQTT transport
- Subscriber discovery/configuration expectations
- Message and transport security

Estimated effort: medium to high.

## 8. Industry-specific protocol packs

These should be implemented when a target market or customer justifies them.

### BACnet/IP for building automation

Support BACnet/IP if the simulator targets HVAC, energy management, access control, or smart buildings. BACnet is designed for building automation interoperability. See [BACnet International](https://bacnetinternational.org/about/).

Map canonical tags to:

- Analog Input, Value, and Output objects
- Binary Input, Value, and Output objects
- Multi-state objects
- Device properties
- Change-of-value subscriptions
- Alarms and schedules in later versions

Estimated effort: medium to high.

### DNP3 or IEC 60870-5-104 for utilities

Choose based on region and customer systems:

- DNP3 is strong in North American electric utilities and is also used in water, transport, and oil and gas.
- IEC 60870-5-104 is common for European and international telecontrol systems.

DNP3 includes timestamped events, quality flags, unsolicited responses, control operations, and class polling. The [DNP Users Group](https://www.dnp.org/About/Overview-of-DNP3-Protocol) documents its utility-focused interoperability model.

IEC 60870-5-104 is defined for monitoring and controlling geographically distributed processes in the [IEC standard](https://webstore.iec.ch/en/publication/3746).

These protocols require a richer canonical model containing event classes, cause of transmission, control states, time synchronization, and protocol-specific quality details.

Estimated effort: high.

### EtherNet/IP for factory PLC integration

Support EtherNet/IP when Rockwell/CIP ecosystems are a stated requirement.

Expected scope:

- CIP object model
- Explicit messaging
- Cyclic implicit I/O
- Assemblies
- Connection management
- Electronic Data Sheet considerations
- Scanner and adapter simulation roles
- Conformance and licensing review

Estimated effort: high.

### Siemens S7 and PROFINET

Treat S7 as the more practical customer-driven simulator candidate for the automotive vertical. Define exact target PLC families and Brabo.io connection mode before selecting an open-source implementation.

Defer PROFINET unless it becomes a concrete requirement.

PROFINET includes real-time Ethernet behavior, device profiles, engineering integration, and certification expectations. PI recommends certification during device development; see the [official PROFINET certification guidance](https://www.profibus.com/download/how-to-get-a-certificate-for-a-profinet-device).

S7 communication is useful for Siemens-focused environments but is narrower and introduces compatibility and maintenance work across PLC generations.

Estimated effort: very high.

## 9. Protocol, scenario, and tag configuration

Configuration should evolve toward independently configurable scenarios. A scenario selects exactly one protocol and owns its tag list:

```json
{
  "name": "reactor-modbus-load",
  "protocol": "modbus_tcp",
  "protocol_config": {
    "host": "0.0.0.0",
    "port": 1502,
    "unit_id": 1
  },
  "tags": [
    {
      "key": "reactor_temperature",
      "name": "Reactor Temperature",
      "data_type": "float32",
      "writable": true,
      "engineering_unit": "degC",
      "mapping": {
        "area": "holding_register",
        "address": 100,
        "word_order": "big"
      },
      "signal": {
        "pattern": "sinusoid",
        "update_interval_ms": 250,
        "amplitude": 8.0,
        "offset": 75.0,
        "period_s": 120.0
      }
    }
  ]
}
```

Do not place passwords, private keys, or DCOM credentials in the public configuration response. Store secret references or use environment/deployment secrets.

Dashboard additions:

- Create, clone, import, export, enable, and disable scenarios
- Select one protocol per scenario
- Add, edit, duplicate, bulk-generate, import, and delete tags
- Protocol-aware tag mapping fields and validation
- Per-tag name, key, data type, access, unit, description, scale, signal, update interval, quality, and metadata
- Per-protocol state: disabled, starting, connected/listening, degraded, stopped
- Endpoint or broker address
- Client/session/connection count
- Protocol-specific operation counters
- Queue depth, dropped/coalesced updates, and reconnects
- Write/command origin and configured persistence behavior
- Downloadable effective tag map for the selected scenario

The aggregate operation count should not hide protocol behavior. Preserve separate counters and provide a clearly labeled aggregate.

Because Brabo.io is the consumer, collect server-side or publisher-side evidence of delivery: connected Brabo.io clients, requests served, subscriptions/monitored items, bytes/messages sent, broker acknowledgements, command/write activity, and last-consumption time where the protocol exposes it.

## 10. Fault injection by protocol

Keep common failure controls and add protocol-specific modes.

| Protocol | Useful failure modes |
| --- | --- |
| OPC-UA | Bad NodeId, bad writes, session closure, delayed service response, stale value |
| Modbus TCP | Exception code, invalid address, delayed response, dropped connection, truncated/malformed test response |
| MQTT/Sparkplug | Broker disconnect, publish loss according to QoS, delayed birth, bad sequence, stale/death state |
| OPC-DA research | Bad quality, rejected write, connection loss, stale value |
| BACnet/IP | Reject reason, timeout, stale property, COV interruption |
| DNP3/IEC 104 | Link loss, stale/event backlog, time skew, select-before-operate failure |

Unsafe malformed-packet modes should be disabled by default and clearly separated from normal interoperability testing.

## 11. Testing strategy

Every adapter needs:

- Unit tests for type, address, quality, and timestamp conversion.
- Contract tests against the canonical tag/value interfaces.
- Integration tests using an independent client implementation.
- Start, stop, restart, reconnect, and partial-failure tests.
- Load tests at 100, 1000, and 5000 tags where supported.
- Bounded queue and slow-consumer tests.
- Independent tag-catalog tests for each protocol.
- Optional cross-protocol consistency tests only for scenarios that explicitly link signals.
- Security configuration and negative-authentication tests.

The central delivery assertion should be:

```text
For every configured scenario and tag, Brabo.io receives the expected value,
type, address or topic, timing, and quality semantics within the scenario's
documented protocol conversion and latency bounds.
```

Test each adapter against Brabo.io in CI or a repeatable integration environment. Independent third-party clients are useful diagnostics but are not the release authority for this internal product.

## 12. Recommended delivery sequence

### Phase 1: OpenOPC compatibility and common cache

- Introduce `TagCatalog`, `ValueStore`, quality, source timestamp, and sequence.
- Extract signal patterns from direct OPC-UA writes.
- Convert OPC-UA into the first `ProtocolAdapter`.
- Expose the live cache through `OpenOPCAdapter` and Pyro on TCP 7766.
- Validate `list`, `read`, and `write` with Brabo.io.
- Add adapter state and metrics APIs.
- Preserve all existing OPC-UA behavior.

### Phase 2: Modbus TCP

- Add stable register mapping.
- Implement Modbus server operations.
- Instrument Brabo.io connections and requests.
- Add optional virtual clients for self-test.
- Add protocol-specific faults, metrics, and dashboard controls.
- Publish the register map through API and downloadable documentation.

### Phase 3: MQTT and Sparkplug B

- Add broker configuration and secure credential handling.
- Implement simple JSON mode.
- Implement Sparkplug birth/data/death and command behavior.
- Add reconnect, buffering, fault injection, and metrics.

### Phase 4: automotive protocol selection

- Use observed Brabo.io/customer demand to select EtherNet/IP or Siemens S7.
- Confirm an actively maintained open-source implementation works on Ubuntu containers.
- Implement the smallest Brabo.io ingestion profile rather than the entire protocol family.
- Validate with the exact Brabo.io connector before expanding scope.

### Phase 5: optional extension

Choose one based on confirmed demand:

- BACnet/IP for building automation
- DNP3 or IEC 60870-5-104 for utilities
- OPC-UA PubSub for OPC-UA streaming and one-to-many delivery
- OPC-DA only as a time-boxed Linux/open-source feasibility spike

## 13. Recorded decisions and remaining questions

Recorded decisions:

1. Product purpose: generate industrial traffic for consumption by Brabo.io.
2. Core industries: chemical, pharmaceutical, and automotive.
3. First added interface: OpenOPC/Pyro on TCP 7766 backed by the live tag cache.
4. Tag model: protocol and all relevant tag information are operator-configurable.
5. Cross-protocol tag equality: not required.
6. Dependency policy: open-source components only; avoid commercial toolkits.
7. Runtime: Ubuntu 22.04 or a similar Linux container.
8. Certification: formal certification is not required; Brabo.io interoperability is required.

Remaining questions should be resolved per protocol rather than blocking the common core:

1. Which Brabo.io connector versions and exact profiles are the integration-test targets?
2. What practical maximum tag count, update rate, connections, and soak duration must each scenario support?
3. Does one process need to run multiple scenarios or protocols concurrently, or is one active scenario per container sufficient?
4. Which authentication and encryption modes does Brabo.io require for each protocol?
5. Should configuration persist locally, be imported/exported as files, or come from a Brabo.io test API?
6. For writes/commands from Brabo.io, should the written value persist, alter the signal state, or be overwritten on the next producer tick?

Complete Brabo.io validation of the OpenOPC compatibility layer, then proceed with the scenario/tag common core, Modbus TCP, and MQTT/Sparkplug B. Keep native OPC-DA COM/DCOM outside the committed scope unless a Linux/open-source feasibility spike is explicitly approved.
